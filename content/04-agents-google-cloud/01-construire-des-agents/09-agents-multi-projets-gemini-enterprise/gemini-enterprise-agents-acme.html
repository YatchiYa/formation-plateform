Le catalogue des agents

Un dossier par agent dans agents/trio/, décrit dans catalogue.json (nom, description, questions d'exemple, et le bloc oauth). Scripts et Terraform lisent ce fichier.

À savoir

L'API de Gemini Enterprise (streamAssist) ne sait pas appeler un agent A2A ou ADK ajouté à l'app (documentation Google). Un agent personnalisé se teste dans le chat, ou en appelant l'agent directement comme le fait l'app (onglet Dépannage).

1 · Projet des agents

Déployer un agent

Tout se fait depuis un terminal Mac ou Linux. Il n'y a pas de Docker : l'image est construite par Cloud Build, dans Google Cloud. L'app n'a pas besoin d'exister à cette étape.

Le poste

  • gcloud connecté : gcloud auth login et gcloud auth application-default login
  • Python 3.12 à 3.14
  • Mac sans droits d'installation : pip install --no-deps -r agents/trio/requirements-poste.txt

Vos droits

Vérification en lecture seule, groupes compris :

./scripts/verifier_droits.sh

La configuration

Un fichier config/12-1-agents-dans-projet-exp.env. Les champs de l'app peuvent rester vides tant qu'on ne publie pas.

Charger la configuration

source scripts/config.sh config/12-1-agents-dans-projet-exp.env

Affiche un résumé : projets, agents, et « (pas encore : agents seuls) » si l'app est vide.

Préparer (une fois par projet)

./scripts/deployer_shell.sh preparer   # filtres Model Armor, dépôt d'images, compte de construction

Déployer l'agent

./scripts/deployer_shell.sh cloudrun {{K}}   # A2A : image (Cloud Build), compte, service privé
./scripts/deployer_shell.sh runtime {{K}}    # et/ou Agent Runtime
== {{K}} (Cloud Run)   adresse {{URL}}
-- 1/3 l'image, construite par Cloud Build (environ 1 min 20 s)   … SUCCESS
-- 2/3 son compte de service et ses 3 rôles
-- 3/3 le service Cloud Run (privé)
Service URL: {{URL}}

Tester (3 à 5 minutes après)

./scripts/deployer_shell.sh tester {{K}}

« OK : les agents répondent en A2A v0.3, avec mémoire de conversation ». Pour un agent OAuth, la réponse « cliquez sur Autoriser » est normale : le test n'envoie pas de jeton utilisateur.

La fiche pour Gemini Enterprise

./scripts/deployer_shell.sh carte {{K}}

Écrit carte-{{K}}.json et affiche tout ce qu'il faut coller dans l'app : nom, description, carte sur une ligne, chemin Agent Runtime, étape Authentification, questions proposées, droits.

La carte vient de carte_a2a.py, au format attendu par Google. Pas celle de /.well-known/agent-card.json : elle a des champs en plus, et Gemini Enterprise la refuse.

Relancer est sans danger : ce qui existe est gardé. cloudrun reconstruit l'image : nouvelle révision, même adresse. Supprimer : python scripts/nettoyer.py --agent {{K}} --supprimer (affiche d'abord l'inventaire).

Choisir les agents dans la configuration

AGENTS="{{K}}"                  # ce qui doit EXISTER (vide = tout le catalogue)
AGENTS_OAUTH="{{K}}={{AUTH}}"   # seulement pour un agent OAuth

Appliquer

source scripts/config.sh config/12-1-agents-dans-projet-exp.env
cd 01-bis-cloud-run-a2a/terraform     # Agent Runtime : 02-bis-agent-runtime/terraform
terraform init && terraform plan     # 1 agent sans app : 22 to add ; +7 par agent
terraform apply

for_each sur le catalogue : une image par agent, et ajouter un agent n'en touche aucun autre. Les agents OAuth ont aussi leurs API Google activées.

Lire ce qu'il faut pour l'app

terraform output cards    # la carte de chaque agent A2A
terraform output oauth    # autorisations attendues + portées
terraform output agents   # (02-bis) le chemin de chaque agent Agent Runtime

Avec PUBLIER=oui et les valeurs de l'app, Terraform ajoute aussi les agents à l'app, autorisation comprise.

L'image

Cloud Build se lance depuis le terminal (aucun bouton console ne prend notre dossier) : gcloud builds submit … --config=01-bis-cloud-run-a2a/cloudbuild.yaml. Le guide 12-1-3 donne la commande complète.

Le service Cloud Run

🔎 Cloud Run → Déployer un conteneur → l'image → nom {{K}}-a2a-shell → région {{REGION}} → Exiger l'authentification → compte de service de l'agent → variables (fichier env-{{K}}.yaml).

Vérifier

L'URL du service doit être exactement {{URL}} : elle est écrite dans la carte.

Détail clic par clic : docs/12-1-3-deployer-agents-console.md.

2 · Projet des agents + projet de l'app

Brancher l'agent sur l'app

Trois choses : les droits du compte de l'app (dans le projet des agents), l'ajout de l'agent (dans l'app), l'accès des utilisateurs. Attendez 2 à 3 minutes après les droits.

Droit ① · agents A2A

Cloud Run Invoker sur le service

🔎 Cloud Run → {{K}}-a2a-shell → Sécurité → Ajouter un compte principal → {{GE_SA}} → rôle Cloud Run Invoker (Demandeur Cloud Run) → Enregistrer.

gcloud run services add-iam-policy-binding {{K}}-a2a-shell \
  --region={{REGION}} --project={{PROJET_AGENTS}} \
  --role=roles/run.invoker --member=serviceAccount:{{GE_SA}}
Droit ② · agents Agent Runtime

Discovery Engine Service Agent sur le projet

🔎 IAM → Accorder l'accès → {{GE_SA}} → rôle Discovery Engine Service Agent. Une fois pour tous les agents.

gcloud projects add-iam-policy-binding {{PROJET_AGENTS}} --condition=None \
  --role=roles/discoveryengine.serviceAgent --member=serviceAccount:{{GE_SA}}

Voir les droits (lecture seule) : IAM → cocher « Include Google-provided role grants » → filtre gcp-sa-discoveryengine. Ou ./scripts/connecter_app.sh verifier. Les deux droits en une commande, avec confirmation : ./scripts/connecter_app.sh droits {{K}}.

La carte, sur une ligne

./scripts/deployer_shell.sh carte {{K}}     # ou : cat carte-{{K}}.json

Dans l'app

🔎 Gemini Enterprise → l'app → Agents → + Add agent → Custom agent via A2A → collez toute la ligne, du premier { au dernier } → Preview agent details → Next.

Authentication

Agent sans OAuth : Skip & Finish. Agent OAuth : ne pas cliquer Skip, voir l'onglet 3.

Le nom

L'agent → Edit → {{NOM}} (A2A). Ou en une commande, avec les questions proposées : onglet 5.

Le chemin de l'agent

./scripts/deployer_shell.sh carte {{K}}     # « [Agent Runtime] projects/{{NUM_AGENTS}}/locations/{{REGION}}/reasoningEngines/… »

Dans l'app

+ Add agent → Custom agent via Agent Runtime → Authorizations : rien (sans OAuth) → Next → Agent name {{NOM}}, description du catalogue, Agent Runtime resource path → Create.

Nouvelle version ?

Agent Runtime crée une nouvelle ressource. Retirez l'ancienne entrée de l'app et ajoutez le nouveau chemin.

L'accès des utilisateurs

L'agent → User permissions → Add → un groupe (recommandé) ou une adresse → rôle Agent User → Save. Sans ce rôle, l'agent n'apparaît pas dans le chat.

Le test

Overview → lien de l'app web → Agents → {{NOM}} → « {{EX}} ». 20 à 40 s la 1re fois (démarrage).

Ce qu'on envoie aux équipes qui ont leurs propres agents

Leur agent est dans leur projet. Elles donnent le droit, puis nous envoient la carte ou le chemin :

Pour brancher votre agent sur l'app Gemini Enterprise ({{PROJET_APP}}), merci de :
1. donner au compte {{GE_SA}}
   - roles/run.invoker sur votre service Cloud Run (agent A2A), ou
   - roles/discoveryengine.serviceAgent sur votre projet (agent Agent Runtime) ;
2. nous envoyer la carte A2A (JSON, une ligne) ou le chemin projects/…/reasoningEngines/… ;
3. si l'agent agit avec le compte de l'utilisateur (OAuth) : l'ID client, et les portées voulues (le secret par un canal sûr).
Région de l'agent : europe-* (app en {{GE_LOCATION}}).

4 · Google + Atlassian + …

Plusieurs fournisseurs d'identifiants

Une autorisation = un fournisseur. Une seule autorisation Google couvre Gmail, Agenda, Drive, Sheets et BigQuery : les portées s'additionnent dans un seul consentement. Un autre fournisseur, comme Atlassian, Airtable ou Databricks, demande une autre autorisation.

A2A (Cloud Run)

Une seule autorisation par agent

L'app envoie un jeton (agentAuthorization). Plusieurs fournisseurs ? Un agent par fournisseur : « Espace Google (A2A) » et « Jira (A2A) ». Le chat passe de l'un à l'autre.

Agent Runtime

Une liste d'autorisations

L'app envoie un jeton par autorisation (toolAuthorizations). Chaque outil prend le sien. L'utilisateur clique « Autoriser » une fois par fournisseur.

La règle de nommage (notre code)

AUTH_ID="acces-google,acces-atlassian" : les outils Google prennent le jeton de la 1re autorisation, les outils Atlassian celle dont l'ID contient « atlassian ». Donc : Google en premier, et le mot du fournisseur dans l'ID.

L'application OAuth Atlassian

  1. developer.atlassian.com/console/myapps → Create → OAuth 2.0 integration.
  2. Permissions : Jira API (read:jira-work, read:jira-user), Confluence API (search:confluence, read:confluence-content.summary).
  3. Authorization → Callback URL : https://vertexaisearch.cloud.google.com/static/oauth/oauth.html.
  4. Settings : Client ID et Secret. Distribution → Sharing : sinon, vous seul pouvez autoriser.

Déployer sur Agent Runtime avec les deux autorisations

AGENTS_OAUTH="workspace=acces-google,acces-atlassian" ./scripts/deployer_shell.sh runtime workspace
AGENTS_OAUTH="workspace=acces-google,acces-atlassian" CLIENT_ID={{CLIENT_ID}} ./scripts/deployer_shell.sh carte workspace

6 · Sécurité et gouvernance

Ce qui protège, à chaque étage

Services privés

Cloud Run sans accès public : seuls les comptes qui ont run.invoker appellent l'agent, c'est-à-dire l'app et vous.

Droits minimaux

Chaque agent a son compte, avec 3 rôles : Gemini, journaux, Model Armor. Le compte de l'app n'a que ① et ②.

Model Armor

Questions et réponses filtrées : injection de consignes, jailbreak, URL malveillantes, données sensibles, contenus dangereux.

Les droits de l'utilisateur

Avec OAuth, l'agent ne voit que ce que l'utilisateur voit. Le jeton n'est jamais enregistré (état temp:) ni écrit dans les journaux.

Portées minimales

Lecture seule partout, sauf Sheets. Aucun outil de suppression. Consentement Interne : comptes Acme uniquement.

Injection par le contenu

Un e-mail peut contenir « ignore tes règles ». L'agent traite ce contenu comme une donnée. Même trompé, il ne peut rien supprimer ni envoyer : les portées et le code l'en empêchent.

Le client OAuth : dans quel projet ?

Projet des agents (recommandé)Projet de l'app
API Gmail, Drive… à activerprojet des agents (script, Terraform)projet de prod de l'app
Quotas, suiviprojet des agentsprojet de l'app

Les deux marchent. Projet des agents : un client par équipe ou par famille d'agents. Projet de l'app : seulement pour un client commun, géré par l'équipe Gemini Enterprise. Dans les deux cas, l'admin Google Workspace peut devoir approuver l'ID client (Sécurité → Contrôles des API).

En production

Lecture d'abord (connecter_app.sh verifier, autorisation_oauth.sh list, nettoyer.py sans --supprimer). Toute modification de l'app demande une confirmation (taper l'ID du projet, ou « oui »). personnaliser_agent.sh garde l'avant pour revenir en arrière.
